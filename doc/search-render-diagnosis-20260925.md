# 検索画面の描画計測と検索語照会の改善

## 本番の読み取り専用計測

ChromeのSSHで既存接続を利用。READ ONLYトランザクション、SQL上限5秒、
ロック待ち上限1秒、プロセス上限60秒。データ本文・SQL本文・認証情報は出力せず、
既知の処理名と数値だけを集計した。計測用Rubyプロセスは終了済み。

- Server3の「東京」先頭20件: 人気順4.613ms、新着順8.820ms。
  いずれもIndex Scan。前回追加した並び順の索引利用を確認。
- Server2のアプリ内部GET（人気順、同じ計測プロセスで2回）:
  初回1541.21ms、2回目104.69ms、両方HTTP200。
- 初回の総件数集計1044.87ms。2回目は30秒キャッシュによりこのSQLなし。
- 2回目の一覧partial6.55ms、検索フォームpartial16.41ms。
- 2回目のDB時間: users11.75ms、events4.42ms、prefectures6.25ms、
  user_tags2.64ms、tags2.17ms、categories2.01ms。
- 保存済み検索語の照会（db_keywords）は初回36.63ms、2回目33.64ms。
- db_keywordsは241553行、検索語最大306バイト。keywordの単一列索引なし。
  別途EXPLAIN ANALYZEした同一検索語の照会はGatherを伴い115.263ms。

各値は単発測定。アプリ内部GETはUnicornの待ち行列・LB・ネットワーク・ブラウザの
画像やJavaScript処理を含まない。新しいRubyプロセスの初回にはクラス/テンプレート
読込みも含む。partial時間には中で実行したDB時間を含むため、DB時間と加算しない。
初回の探索的計測でtemplateとpartialイベントを二重集計した値は採用していない。

## 今回の修正

`db_keywords.keyword` の完全一致照会用に、非ユニークHash索引をCONCURRENTLYで追加。
現行モデルは検索語長を制限していない。将来の長い検索語でB-treeの索引値サイズ制限に
抵触しない方式を選んだ。検索条件・大文字小文字の扱い・重複許可・登録値は変更しない。
追加拡張・外部サービス・新プランなし。

根拠: [PostgreSQL12 Hash索引](https://www.postgresql.org/docs/12/hash-intro.html)、
[CONCURRENTLYの仕様](https://www.postgresql.org/docs/12/sql-createindex.html)。

## ローカル検証とリリース条件

- 専用PostgreSQL16の合成データで17テスト、1227アサーション成功。
- 日本語・大文字小文字・空文字・NULL・重複・長い検索語（12800文字）の検索結果一致。
- 索引作成後の長い検索語の追加も成功。作成・再実行・削除とタイムアウト復元を確認。
- 同名の別定義索引があれば削除せず停止する。
- 合成24万件の照会: 22.711→0.037ms、索引利用を確認。本番改善率の保証ではない。
- 本番DDLは索引1本追加。作成中と更新時のDB負荷・容量は増える。
  ロック待ち5秒、SQL上限10分。失敗時は後続デプロイを止めて状態確認する。
- 誤動作時は実行計画とDB負荷を確認し、追加索引のオンライン削除を影響確認後に判断。

## 残る要因

初回の検索総件数集計は依然として主要な待ち時間。30秒キャッシュは各Unicornプロセス内で、
プロセス間共有ではない。今回の計測では一覧描画・関連取得に秒単位の遅延は再現しなかった。
短い日本語の部分一致をさらに高速化するには、検索意味の一致や更新負荷を検証する必要がある。
CPU stealとブラウザ側の読み込み時間は今回の描画計測だけで解消したとは判断しない。

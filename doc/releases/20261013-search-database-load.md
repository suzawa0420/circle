# 2026-10-13 検索遅延・DB高負荷の調査と修正

## 状態

ローカル実装・検証済み。本番反映は未実施。
対象はサークルブック、Lightsail server4 / server5、共有 circle-db。
基準コミットは ae986bb55。ユーザー申告では数日前から検索・管理・メッセージが遅い。

## 本番の読み取り専用確認

- Webサーバー2台のCPUは余裕があり、使用可能メモリは約2.4〜2.8GB。
  circle-puma / nginxは両方active、server4のRedis接続は0。
- DBの1日グラフはほぼ80〜100%、特に直近は100%付近。Redis削除前から続く。
- 直近15分のNginx集計では検索の中央値がserver4で8.418秒、server5で9.645秒。
  p95はそれぞれ26.041秒、26.742秒。別時刻の短い標本で、同一条件のA/B比較ではない。
- 公開healthは6.047秒。内部healthも4.161秒、別の測定では11.472秒を観測。
  空いている時は約3〜4ms。同じプロセス群が遅い検索で埋まり、他画面も待つ状況と整合する。
- pg_stat_activityの複数標本で、10〜14接続がキーワードLIKE・標準順・ページングの
  SELECTを実行中。最長約7〜9秒。ロック待ちではなく実行中の分類だった。
- 「東京」、標準順、20ページ目のEXPLAIN ANALYZEは1981.423ms。
  既存index_users_on_switch_and_last_post_descの走査で1917.664ms、
  400件採用するまでに6243件をFilterで除外。紹介文の正規表現を含む公開条件を再評価する。
- 公開件数用の部分索引は利用されているが、並び順用の既存索引には公開条件がない。
- pg_stat_statementsの分類は5秒で打ち切り。SQL全体の累積寄与率は未確定。

DB診断はREAD ONLY、statement_timeout 3〜5秒、lock_timeout 1秒、
プロセス45秒で制限。SQL本文、入力値、利用者データ、認証情報は出力していない。
管理画面やメッセージを本人として操作したわけではなく、既存アクセスの分類集計による確認。

## 修正

公開条件を既存の公開件数用索引と同じ述語に固定したB-tree部分索引を2本追加する。

- index_users_public_on_switch_last_post: switch ASC, last_post DESC
- index_users_public_on_switch_created_at: switch ASC, created_at DESC

公開可能なサークルだけを並べて索引化することで、順序付き走査中の紹介文再判定を省く。
主催者の公開可否は従来どおりクエリ時に判定する。検索の条件、順序、ページ数、
既存キャッシュTTL、アカウント認証、料金プランは変更しない。
既存索引を残すので、公開対象以外を扱う管理画面のクエリも維持される。

## 本番反映と復旧

対象ブランチmasterへのコミット・pushで既存GitHub Actionsが起動する。
新規DBマイグレーション20261013020000で2本をCONCURRENTLY作成する。
行データの追加・更新・削除、バックフィルはない。作成中はDB CPU/I/O負荷が増える。
各SQLは最大10分、ロック待ちは5秒。既存名や無効な部分作成があれば停止し、
自動で索引を削除したり成功扱いしたりしない。途中失敗時は状態を確認して復旧する。

既存手順で2台を順次Pumaホットリスタートし、HTTPとhealthを確認する。
この差分にはアセット変更がなく、既存スクリプトのアセット再生成条件には該当しない。
計画停止は設けないが、DB負荷増加や切り替え中の一時的な応答遅延はあり得る。

反映後、同じ検索の実行計画・応答時間、DB CPU、両ホストのアクセス集計を確認する。
問題があれば、このマイグレーションのdownで追加2索引だけをCONCURRENTLY削除して
旧計画へ戻す。旧索引と行データは残る。コードは必要に応じて変更をrevertして再反映する。

# 公開サークル一覧の件数集計を共有

## 調査（2026-10-02、16:18〜16:31 JST）

LightsailのブラウザSSHで本番を読み取り調査した。
server4のロード平均は0.77 / 0.82 / 0.74、利用可能メモリ2675MB、
server5は0.55 / 0.41 / 0.47、利用可能メモリ3027MB。両方のディスク使用率は5%。
この短い観測ではリソース枯渇は見られない。CPUバースト残量や過去のピークは未確認。

server4の直近5000リクエストを、個人情報を出力せずパス別に集計した。
`/circles/search` は37件で中央値4.708秒、p95は20.375秒、
`/circles` は16件で中央値3.234秒、p95は7.071秒だった。
期間の固定されていない少数標本であり、全体のSLOや恒常的な速度を示すものではない。

読み取り専用トランザクションのRailsリクエスト計測で、`/circles` は200、1.054秒。
User Countが495msを占め、User Loadは7msだった。
COUNTのEXPLAIN ANALYZEではusersとadmin_usersの並列全走査・ハッシュ結合を確認し、
689.8ms、読み込みブロック0（共有バッファからの処理）だった。
公開条件のHTML除去・日本語判定と主催者判定を、ページ件数計算のたびに実行している。

## 変更

キーワード検索専用だった既存のSearchResultCountCacheをCircleListingDataで適用し、
同じ共通一覧を使う公開一覧・地域・種目・タグのページ送りでも利用する。
条件を含むSQLをキーに、件数のみ30秒、プロセス当たり最大4MBのメモリに保持する。
投稿、公開可否、認証情報はキャッシュしない。件数・ページ数だけは最大30秒古い場合がある。
初回やキャッシュ切れ時の集計コストは残る。新しいDB migrationは不要。

本番の独立した読み取りプロセスで、同じ8995件の集計が初回1.0217秒、
キャッシュヒット0.00054秒になった。これは件数計算のみの測定であり、
ページ全体の改善率ではない。本番のアプリコード・サービス設定は変更していない。

## 検証

隔離した一時PostgreSQL16の合成データで実施。本番DBや認証設定は使わない。

`bundle exec ruby test/performance/search_queries_check.rb <専用一時DBソケット>`

18 tests / 1369 assertions、失敗・エラーなし。
ページ間再利用、検索条件の分離、TTL満了、最新レコードの取得、
投稿の確認待ち化と主催者の公開停止、既存検索の並び順・ページングを検証した。
古いテスト用モデルには公開条件がなかったため、現在のモデルの公開scopeを読み込むよう更新。

## 反映後の確認

今回の作業はコミットまで。本番反映後は両サーバーの同じ時間帯の応答時間を比較する。
検索の初回遅延、リクエスト待ち、広告などブラウザ側の遅延は今回の修正だけで解消したとは言えない。
回帰があればこの変更をrevertして通常のデプロイを行う。DBの復元は不要。

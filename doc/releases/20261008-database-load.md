# 2026-10-08 DB高負荷対策

## 本番で確認した事実

- 対象: circle-book.com、Lightsail server4 / server5、共有 circle-db。
- 両アプリサーバーは稼働。空き相当メモリは約3〜4GB。server4のCPUバースト残量は約33%で未枯渇。
- circle-db のCPUは8:20〜8:30頃と8:55〜9:05頃（JST）にほぼ100%。
- server4の当日access.logの9:00〜9:05集計: 3,169件、平均4.204秒、p95 21.652秒、499/5xx計154件。
- 9:05〜9:10は1,883件、平均0.190秒、p95 0.624秒、499/5xxは0。調査中に自然回復しており、修正の成果とは扱わない。
- スケジュール詳細への多数のアクセスを確認。UAにGPTBot・Ahrefs等を含むが、UAだけで実際の運営元とは断定しない。
- 本番の読み取り専用EXPLAIN ANALYZEでは、`User.publicly_visible`のCOUNTが961.691ms。紹介文の正規表現を含む並列全件走査が発生。
- 現在のログファイルはUTC 00:00以降のみ。指定した「直近1時間」が完全な1時間分の標本であるとは限らない。
- pg_stat_statementsは別スキーマに存在するが、本文を取得しない分類クエリも5秒でタイムアウト。累積SQL全体の寄与率は未確定。

ログ本文、クエリ文字列、認証情報、個人の回答は出力していない。集計と数値のみ取得。診断用RailsプロセスはDBを読み取り専用、SQLを5〜8秒制限にした。

## 変更

1. 公開サークルの厳密な既存条件を部分索引の述語にし、`users(id, admin_user_id)`を並行作成する。紹介文判定は書き込み時に索引を更新し、検索・件数取得のたびに全件のHTMLを処理しない。
2. 公開条件の定数だけをSQLリテラルにし、generic prepared planでも索引を利用可能にする。主催者の公開状態は引き続き実クエリで判定し、キャッシュや判定省略は導入しない。
3. スケジュール詳細の関連一覧は表示列だけを一度取得する。回答の全文・レコードを展開せず、参加人数をGROUP BYで一括集計する。予定の件数、順序、過去ページの区切りは維持。

## 検証

- 合成DBで公開条件・ブログ・検索・スケジュール・ランキング: 43 tests / 513 assertions成功。
- 少量のfixtureで別索引と追加ソートを選ぶことがある既存ランキング試験は、追加ソートを抑止して「ランキング用索引で順序を満たせるか」を検証するよう安定化。本番のプラン設定は変更しない。
- 合成15,000件と境界条件の索引試験: 1 test / 9 assertions成功。結果3,002件は変更前後で一致。
- 合成COUNT実測: 411.592ms → 0.460ms。generic prepared planは0.385ms。索引の利用、主催者の非公開化の即時反映、索引のdown、タイムアウト復元を確認。
- 合成の速度比をそのまま本番の改善率とは扱わない。本番反映後に同じCOUNTとHTTP、両サーバーのエラー・時間を再測定する。

## リリース内容と復旧

対象ブランチはmaster。既存GitHub Actionsのテスト後、両サーバーでコードと既存アセットを保持したアセット生成を準備し、1台ずつPumaをホットリスタートする。
新規DB処理は索引20261010000000のCONCURRENTLY作成のみ。レコード更新・削除やバックフィルはない。索引作成時は一時的なDB CPU/I/Oの増加があり、lock_timeout 5秒、statement_timeout 10分で停止する。失敗時は無効な索引を自動削除・黙認せず、展開を停止する。
計画停止時間なし。課金プラン、DNS、ファイアウォールは変更しない。
アプリの問題はこの変更をrevertして既存ローリング手順で戻す。追加索引は残しても旧コードと互換で、データ復旧は不要。索引自体の撤去が必要な場合は対象を確認してCONCURRENTLYで削除する。

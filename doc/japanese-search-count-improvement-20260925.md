# 日本語検索の総件数集計を軽量化

## 原因と採用した修正

検索対象の `name` と長い `appeal` を各行で `LOWER()` していた。
「東京」「初心者」のように大小文字のない語でも、紹介文全体の変換コストが発生する。
`User.search_word` で、文字範囲 `ぁ-んァ-ヶ一-龥ー` のみからなる検索語は
この2列をそのままLIKE比較する。それ以外は従来どおりLOWERを使う。

英字混在・ギリシャ文字・アクセント文字・全角英字・空文字・LIKEワイルドカード・
エスケープ文字は最適化対象外。検索語は引き続きバインドし、SQL式には固定値しか使わない。
部分一致・複数語AND・関連テーブルOR・公開条件・並び順・ページ数は変えない。
30秒の総件数キャッシュも変更しない。DBのDDL、設定変更、新サービスの追加なし。

参考: [PostgreSQL12の文字列関数](https://www.postgresql.org/docs/12/functions-string.html)、
[Unicodeの特殊大小文字変換](https://www.unicode.org/Public/UNIDATA/SpecialCasing.txt)。
大小文字のない文字範囲に限定し、未知の文字を広く「日本語」と推定しない。

## 本番の読み取り専用比較

READ ONLY・REPEATABLE READ、SQL上限5秒、ロック待ち1秒、プロセス上限60秒。
旧→新→新→旧のABBA順。同じスナップショット内で比較し、SQLキャッシュを使わず実行。
実データ・SQL本文・秘密情報は出力せず、時間と一致判定のみを出力。

| 接続元・検索語 | 旧SQLの2回（ms） | 新SQLの2回（ms） |
|---|---:|---:|
| Server3・東京 | 1415.25 / 2060.28 | 515.50 / 499.56 |
| Server2・東京 | 2201.81 / 950.30 | 409.58 / 330.82 |
| Server2・初心者 | 839.64 / 658.89 | 283.22 / 255.64 |
| Server2・東京 初心者 | 907.93 / 1650.24 | 359.48 / 398.21 |

すべて件数一致。Server2で3条件の全検索対象IDを別途比較し、すべて完全一致も確認した。
ID自体は出力していない。DBは共有であり、接続元が異なるだけで独立したDBの試験ではない。
負荷変動がある少数計測なので、本番全体の改善率・CPU削減率・応答時間の保証ではない。

## 不採用とした案

関連テーブルORを先に置く案は、Server2の一部検索では短縮したが、Server3の東京は
旧1085.12/1289.53msに対し新1166.48/1312.09msで、安定した改善を確認できなかった。
この変更は取り除いた。前回の複数語比較の計測コード修正後は3条件とも件数一致を確認。

## 回帰テストと復旧

専用PostgreSQL16の合成データのみ使用。旧テキストSQLをテスト内に独立して固定し、
実装同士の自己比較にならないようにした。各検索列と関連先、NULL、重複、大小文字、
Unicode、ワイルドカード、複数語、3種類の並び順、ページング、30秒キャッシュを検証。
日別一覧を含む28テスト・2543アサーション成功。
人気順・新着順の索引検証も20テスト・2044アサーション成功。

masterへのpush後に既存GitHub Actionsで両サーバーへ反映し、HTTP応答と
アプリ内の総件数SQLを確認する。問題時は今回のコード変更をrevertして再デプロイ。
索引やデータの削除は不要。

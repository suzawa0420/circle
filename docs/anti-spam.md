# 登録・投稿スパム対策

## 調査結果と採用した対策

初回調査後に更新された origin/master には、登録時のTurnstile認証、ハニーポット、登録・ログイン・パスワード再設定の回数制限が追加済み。これらを保持し、同じ AbuseCounterStore に投稿制限を統合した。下記の調査結果は初回調査時点。

- Rack::Attack 6.7.0 は Railtie によって導入されているが、制限ルールが無効だった。
- 登録は主催者・参加者・出展者の3系統。メール確認（Devise confirmable）は未導入。
- サークル・施設口コミの投稿禁止と重複防止が画面表示に依存し、直接POSTで回避できた。
- 口コミを保存後に関連の last を取得していたため、失敗時や同時投稿時に別レコードを更新する危険があった。
- サークル口コミの編集・削除に未ログイン時の認可漏れがあった。
- ブログ作成の権限確認でリダイレクト後も保存処理が継続していた。
- 施設口コミの削除処理が未実装だった。

今回は追加サービス・追加gem・DBマイグレーションなしで次を実装。

1. 全3系統の新規登録、口コミ作成、ブログ作成・編集に、セッション・投稿先に紐づく署名付きフォーム検証（12時間）とハニーポット。
2. 全3系統を合算して接続元IPあたり登録試行10回/時。口コミとブログを合算して送信試行5回/分・30回/時。失敗した試行も含む。超過は429とRetry-After。通常の閲覧・ログインは対象外。
3. 投稿禁止・通報済み接続元・重複投稿をサーバー側でも検証。会員の重複口コミはIPを変えても拒否。
4. 対象サークル・施設をロックし、保存と平均評価の更新を同一トランザクションで実行。投稿IPと平均点のクライアント指定を除去。
5. 口コミの長さ6〜2000文字、評価値の範囲、URL表記の一部（HTTP/HTTPS・www）を検証。日本語以外という理由だけで拒否しない。
6. ブログの所有者・既存アカウント制限をサーバー側で確認。マスター管理者を除き、制限済み主催者は書き込み不可。
7. 施設口コミ一覧にマスター管理者専用の削除リンク。削除後に評価を再集計。既存口コミの一括削除や自動判定による削除は行わない。

## 配信基盤で追加すべき対策（未適用）

国別遮断はアプリ単独で国ヘッダーを信用して実装しない。接続元の国を判定するWAF/CDN側で制御し、オリジンサーバーへの直接アクセスも制限する必要がある。

登録時のTurnstileは最新masterの既存実装を保持する。追加候補は Cloudflare の国別ルールと口コミ・ブログへの人間判定の拡張。今回の変更で新規契約・接続・DNS変更・課金は行わない。

検討する構成：

- 日本国外からの登録・投稿をWAFで拒否し、国内の登録・投稿にも人間判定を重ねる。
- 国外からの閲覧も遮断する場合は、検索エンジンの検証済みクローラーや必要な監視を例外にする。User-Agentの文字列だけで例外化しない。
- 海外滞在者・VPN利用者をどう扱うかを決定する。国別遮断だけでは日本のIPを使うボットは止められない。
- 人間判定を採用する場合は、サーバー側で結果・ホスト名・用途を検証し、検証不能時に投稿を通さない。
- 必要に応じてメール確認を追加する。既存3種類のアカウントとメール配信の運用に影響するため、今回の変更には含めない。

フォーム署名・ハニーポットは画面を取得しない単純なボット向けで、人間判定の代わりではない。回数制限はIP変更や複数サーバーへの分散で回避され得る。スパムの完全防止は保証しない。

## デプロイ前提と運用

デプロイは master へのpushで GitHub Actions deploy_prod が起動し、Server3 → Server2 の順に反映・再起動・応答確認する。既存ワークフローには依存関係確認、マイグレーション、アセット生成、Turnstile設定の引き継ぎも含まれる。

- 本変更の対象は登録と投稿。既存閲覧への国別遮断は追加していない。
- DB変更・gem追加なし。ERB/Hamlの変更のみで静的アセットの生成は不要。反映には全Webプロセスの再起動またはローリング再起動が必要。単一プロセス構成では一時停止の可能性がある。
- 変更前のコミットを記録し、問題時は revert コミットを対象ブランチに反映して同じ手順で再起動する。DBを戻す必要はない。
- 本番のNginx等が接続元IPを正しく転送していることを確認する。アプリへの直接アクセスを防ぎ、訪問者が任意に付けた転送ヘッダーを信頼しない。CDN追加時は信頼するプロキシ設定も確認する。
- 回数カウンターは tmp/abuse_counters に保存。Unicornワーカー間で共有し、既存の64個のシャードファイルのロックで同時加算を直列化する。複数サーバー全体では共有されないため、全体の制限はWAFまたは共有カウンターが必要。
- アプリ実行ユーザーに同ディレクトリの書き込み権限が必要。既存カウンターは書き込み時に期限切れエントリを削除し、ファイル数・エントリ数に上限を持つ。
- 共有キャッシュ/CDNでセッション付きフォームのHTMLをキャッシュしない。公開済みの古いフォームは再読み込みが必要。
- 制限は同じIPを使う学校・会社・携帯回線の利用者にも合算される。導入後は429発生数と登録成功率を確認して調整する。
- スパム判定対象の既存投稿は管理画面で内容を確認して対応する。この変更は既存データを自動削除しない。

## 検証

`bundle exec ruby test/security/run.rb`

既存のfixture・本番設定・認証情報・.envを読み込まず、インメモリSQLiteと最小のRails環境で実際のコントローラー、モデル、フォーム検証、Rack::Attackルールをテストする。カウンターは別プロセス同時実行も検証する。

通常の `rails test` では読み込まない独立スイート。アプリ全体の起動、Deviseによる登録の一連の画面操作、本番のプロキシ構成、PostgreSQLの並行トランザクション、WAF設定を検証するものではない。これらは本番反映前の環境確認が必要。
